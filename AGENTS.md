# Project instructions

- Purpose: dependency-free Python/SQLite backend for the existing `web/index.html` dwell UI.
- Run from the repository root with `python3 -m backend.app`; it listens on `127.0.0.1:8765` by default.
- Run the thinking integration from the sibling `gpt-thinking-block-mcp` checkout with `THINKING_PROMPT_LANGUAGE=zh-CN python3 server.py`; configure `THINKING_MCP_URL` if it is not on port 8787.
- Keep the frontend's existing information architecture and visual details. Backend work must not silently redesign the single-file UI.
- The API contract is the actual `fetch('api/...')` usage in `web/index.html`; demo interception runs only with `?demo=1`.
- Owner-configured embeddings use a separate OpenAI-compatible base/token/model in the existing API settings page. Never return the saved token to the browser; save it only in the mode-0600 SQLite settings store, support `/v1` or full `/embeddings` relay URLs, test with synthetic text, and switch the shared history service without a restart. `DWELL_EMBEDDING_*` environment variables remain the higher-priority server-managed override.
- Runtime data belongs in `data/` and is ignored by Git. Never commit API tokens, the SQLite database, health tokens, uploads, or personal data.
- Bind to loopback by default. Set `DWELL_PASSWORD` or equivalent trusted proxy authentication before any non-loopback exposure.
- Validate path inputs against configured roots. Keep repo browsing read-only and cap file, diff, request, and upload sizes.
- Dwell adapts `gpt-thinking-block-mcp` into a user-visible working-summary tool by overriding its private-scratchpad wording. Both API-backed chat and resident `send_dwell_reply` must validate the original `style` / `thinking` / `effort` / `skin` contract through that service before saving a reply. Keep the existing Dwell `Thought process` UI; do not import the upstream MCP Apps card UI. Resident `enter_dwell` / `read_dwell_messages` must exclude saved `think` rows. Do not expose or label generated text as hidden chain-of-thought.
- The resident MCP uses a generated capability URL because the target ChatGPT connection has no OAuth. Treat the full URL as a credential: never log or publish it, expose only the exact token-shaped `/mcp` route, keep the owner link page bound to the configured signed-in user, and preserve fixed `me`/`gu` roles plus idempotent replies.
- Keep the resident MCP on its dedicated `mcp_chat_id`: its Recents entry, history, pending state, and live events must not take over or leak into API-backed Claude chats. The MCP only bridges an active ChatGPT tool-calling turn; it does not create a permanent server-side model worker.
- The reading-nook upload endpoint accepts TXT, Markdown, or the documented JSON book shape up to 50 MB, writes atomically under `data/books/`, and must never overwrite an existing same-name book.
- Keep shared reading page-driven: the first delivery of a stable `reading:{slug}:{chapter}:{page}` key must enqueue one hidden `nook` event for the dedicated resident chat, independently of whether the floating chat/notebook window is open. Reopen/reconnect must not resend that key; only a page/chapter/book change or explicit force resync may create another delivery. Include the previous page, fixed backend chapter-update rule, and title/summary-only notebook index; mark the last page so the resident can update durable notes idempotently. The floating window has exactly the `聊天` and `记事本` tabs plus an explicit collapse control.
- A book notebook is scoped by slug and stores title/summary/body with user and resident CRUD/pin access. Its initial UI is a title-only directory: title rows are boxes with only a bottom edge and the selected state reuses the reading TOC's `.on` treatment. Selecting a title opens detail, while the create form stays hidden behind a small icon. Mini-chat messages reuse the main chat `.bubble` / `.gu` classes; do not invent a separate black user bubble. Resident search may return only ids/titles/summaries; full body text is returned only by the separate single-note read. Whole-book deletion requires UI confirmation and removes the file plus its progress, annotations, notes, and internal settings; test this against an isolated database and book directory before production.
- Tests: `python3 -m unittest discover -s tests -v`. Syntax: `python3 -m py_compile backend/*.py`. Frontend runtime checks are the five serial `node tests/test_*_runtime.js` scripts; do not run them in parallel on the production host.
- No deployment, service restart, Caddy change, Git commit, push, or PR unless the user explicitly authorizes that separate action.
